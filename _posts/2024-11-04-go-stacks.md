Go can dynamically manage the stack size of Go programs via goroutines, and goroutines, being managed by the Go runtime (rather than being directly mapped to OS threads) allow for a more efficient and flexible stack management strategy. 

While OSs can handle dynamic stack growth for threads (for instance, through page faults), Go's runtime-based approach enables more efficient stack management: stacks start very small (2KB vs megabytes for OS threads), can grow through copying operations, and can shrink during garbage collection.

*Page faults* happen when programs try to access memory that isn't currently mapped. OSs use different protection mechanisms: Windows uses explicit *guard pages* \[2] that trigger exceptions when accessed, while Linux checks if the access is within reasonable bounds of the current stack pointer (`SP - 65536 - 32*sizeof(unsigned long)`) \[3].

`/arch/x86/mm/fault.c` \[3] shows that the Linux Kernel automatically grows the stack to allow for some instructions to work:

{%highlight c%}
if (sw_error_code & X86_PF_USER) {
    /*
     * Accessing the stack below %sp is always a bug.
     * The large cushion allows instructions like enter
     * and pusha to work. ("enter $65535, $31" pushes
     * 32 pointers and then decrements %sp by 65535.)
     */
    if (unlikely(address + 65536 + 32 * sizeof(unsigned long) < regs->sp)) {
        bad_area(regs, sw_error_code, address);
        return;
    }
}
{%endhighlight%}
